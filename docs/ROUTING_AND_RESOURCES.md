# Model routing, optimization, fallback and resource management

## Owner and independent providers

**Boru Core is the routing and scheduling authority for Boru Yolu tasks.** It must function with TIHULU-AUTO uninstalled. TIHULU-AUTO is optional legacy integration, not a required API, process, agent name, routing service or credit source. Jan may be invoked directly; OpenCode is a separate optional agent adapter. Disconnection of either optional agent adapter cannot affect standalone OpenCode/Jan behavior. No silent import of historical TIHULU-AUTO configs or sessions.

## One optimizer plus independent restrictions

Profiles select efficiency; restrictions select *who can receive data and control tools*.

| Mode | Model choice | Parallelism | Cloud spend |
| --- | --- | --- | --- |
| AUTO | Complexity/capability fit, privacy, latency, available budgets | Adaptive | As useful and authorized |
| ECONOMY | Smallest suitable working local model first | Low | Escalate only on justified failure/quality need |
| BALANCED | Capability, cost, time and memory weighted | Moderate | Bounded |
| PERFORMANCE | Strongest capable available authorized models | Up to configured limit | May spend more within hard budget |
| MANUAL | Explicit selected provider/model; no silent override | Explicit | Explicit |

`LOCAL_ONLY` forbids every cloud inference or fallback path. `CLOUD_ALLOWED` permits approved providers only, still filtered by disclosure policy. Security profiles are **not** optimizer presets.

## Model registry and discovery

Use exact IDs from the live Jan `/v1/models` API or supported OpenCode provider inventory; labels are not IDs. Discover capability by bounded text/tool/JSON/multi-turn tests rather than guessing from parameter count. Store source (`discovered`, `configured`, `verified`), max known context, per-model loaded state, memory estimate, current health, supported task tags, last successful tests, actual provider fees where reported and `UNKNOWN` when unavailable.

Useful candidates for tests (not guaranteed availability): Qwen3-Coder, Qwen3.6, Jan 4B, GPT-OSS, Gemma, OrcaRouter variants; cloud GLM, NVIDIA DeepSeek/Nemotron, direct DeepSeek and OpenAI. Never invent available token credits or working model endpoints.

## Routing policy

1. Classify task into capability tags and complexity; identify local/private data dependencies.
2. Eliminate candidates disallowed by inference scope, tools policy, health, memory, context, limits, concurrency or consent.
3. Rank candidates by mode-specific quality/latency/token cost.
4. Obtain resource lease before loading/starting a model.
5. Dispatch a real child session and verify provider/model/session and result evidence.
6. For tools, pass through trusted broker (never free-form direct Shell in restricted mode).
7. Release leases on completion, cancellation, timeout or failure.

A response generated by the coordinator is not proof a child was invoked. Require child session IDs, provider/model evidence and an actual result.

## Token budgets

Track input/output usage and provider costs **only when observable**; mark estimates as estimates. Reserve per-task and per-workflow budgets. Compact context by retaining instruction decisions, state references and minimum relevant excerpts, not full chat logs. Deduplicate requests; use bounded retries and configurable cooldowns. Stop at hard budget. Never retry non-idempotent Shell/file writes on ambiguous failures without authorization.

## Fallback

Classify 429 rate limit, exhausted credits, auth error, timeout, 5xx, missing model, local OOM, malformed output, safety/provider denial, context overflow. Fallback only to a verified authorized compatible model while preserving confidentiality and operation permissions. Model policy blocks are not retryable permission hints. If all cloud providers fail, AUTO can fall back to local models **only if those models satisfy task requirements and permissions**. Fail closed if nothing can.

## Scheduling and resources

Target up to **six agents**, not six heavy local models. Default physical large-model concurrency is one on a 16 GiB VRAM-class device until measured. Track CPU, RAM, VRAM, swap, active inference processes and reservations without polling private inventories into cloud contexts.

- Jan may expose multiple registered models while only some are loaded.
- Never kill an unrelated Jan/OpenCode/desktop model process.
- Idle unloading only with documented engine support, ownership checks, zero active borrowers and explicit timeout.
- On OOM release own reservations, unload only broker-owned idle model, then replan; **never** blindly terminate external processes or force swap thrashing.
- Avoid long-lived models after a cancelled task; resource cleanup must be idempotent and verified.
- OpenCode and Jan retain independent operation when orchestration UI is down.

## Benchmarks

Measure per model: basic chat 3 turns, JSON response, declared tool-calling, coding fixture, cold/warm latency, peak VRAM/RAM and unloaded memory. Compare within task categories. Historical failures are regression tests, not claims about today's versions.
